# ТЗ: Личный кабинет Peremoney (ЛК лидогенерации)

> Источник: `ТЗ_на_ЛК_Peremoney.docx`. Референс интерфейса: https://peremoney.lork.dev/dashboard
> Документ декомпозирован на три слоя: **1) Фронтенд/визуал**, **2) Бэкенд/наша бизнес-логика**, **3) Внешние API-провайдеры (Leads Factory)**.

---

## 0. Цели и суть проекта

**Суть**: личный кабинет (ЛК) для сервиса лидогенерации.

**Функции системы**:

1. Передача лидов (получение из внешнего CRM-провайдера).
2. Загрузка источников и управление источниками.
3. Подсчёт баланса клиента.
4. Дашборд с аналитикой.
5. Передача лидов дальше по API — куда угодно (наружу, любому потребителю).

**Три ключевые задачи проекта**:

1. Реализовать клиентский ЛК по референсу (ссылка выше), связав его по API с реальным ЛК поставщика Leads Factory.
2. Сделать отдельный **мастер-кабинет**, который создаёт другие кабинеты (по сути — логин/пароль + внутренний ID) с разным уровнем доступа: для клиентов и для сотрудников ("работяг").
3. Сделать систему разветвления лидов: лиды приходят по отдельному API из одного проекта-поставщика и распределяются в несколько разных кабинетов (например, чтобы продавать один лид в несколько рук). Технически — разветвление 1 проекта на 3–4 кабинета, связь между которыми настраивается вручную в мастер-кабинете.

**Ключевые вводные (провайдер Leads Factory)**:

- Bearer-токен: `60286a84-65eb-42ae-b0ee-4b33aecd6c3f`
- Базовый URL API: `https://openapi.leads-factory.ru/v1/`
- Тестовый доступ в ЛК поставщика: `https://lk.leads-factory.ru` (логин `sushkevichnikolay`, пароль `Sushkevichnikolay!1`)
- Тестовый доступ в кабинет источников: `http://vdl.leads-factory.ru` (те же логин/пароль)

# 2. БЭКЕНД / НАША БИЗНЕС-ЛОГИКА

## 2.1. Модель доступа и ролей

- Мастер-кабинет создаёт дочерние кабинеты: генерирует внутренний ID, логин/пароль сотрудника (общий на всех сотрудников этого кабинета) и логин/пароль клиента (уникальный на кабинет).
- Уровень доступа хранится на уровне кабинета: `full` (сотрудник) / `limited` (клиент).
- Видимость разделов для `limited`-доступа регулируется набором булевых флагов на уровне кабинета (по разделам: contacts, sources, script, finance, settings). Лиды и Дашборд — всегда `true`, без возможности скрыть.

## 2.2. Разветвление лидов (fan-out распределение)

- Отдельный входящий API (наш собственный, публичный) принимает лиды из одного проекта-источника.
- В мастер-кабинете сотрудник вручную связывает 1 проект-источник с 3–4 дочерними кабинетами.
- При получении лида по входящему API система должна разослать (продублировать) его во все связанные кабинеты согласно настроенной связке "источник → кабинеты".
- Нужно спроектировать: схему хранения связок проект→кабинеты (many-to-many), идемпотентность приёма (защита от дублей при повторной доставке), и лог/аудит того, куда какой лид был отправлен.

## 2.3. Расписание автоматических задач (cron / scheduler)

Все времена — по МСК:

| Время | Задача                                                                                       | Endpoint провайдера                                     |

## 2.4. Формулы дашборда

Все расчёты — за выбранный период (клиентская агрегация из уже выгруженных Контактов/Лидов):

- Получено контактов = `COUNT(Контакты)`
- Квалифицировано лидов = `COUNT(Лиды)`
- Продано = `COUNT(Лиды WHERE статус = "купил")`
- CR в продажу = `Продано / Квалифицировано лидов * 100`
- Выручка = `SUM(Сумма) WHERE статус = "купил"` (по разделу Лиды)
- CPL = `весь потраченный баланс / Квалифицировано лидов`
- Средний чек = `Выручка / Продано`
- Стоимость продажи = `CPL / CR в продажу`

## 2.5. Маппинг статусов контактов (обязательный перевод на русский)

Показываем ТОЛЬКО эти 5 статусов (остальные значения из провайдера — скрываем, показывая пустое место в UI):

| Значение API    | Отображение в ЛК |
| --------------- | ---------------- |
| `new`           | НОВЫЙ            |
| `noAnswerFinal` | НЕДОЗВОН         |
| `recall`        | ПЕРЕЗВОНИТЬ      |
| `notRelevant`   | НЕ КВАЛ          |
| `success`       | КВАЛ             |

Все прочие статусы из справочника провайдера (`client_blacklist`, `experiment*`, `incorrect`, `late_experiment*`, `noAnswer1-7`, `pre-success`, `repeat`, `undistrib` и т.д.) — не отображаются.

Дедупликация: при добавлении новых контактов система убирает записи со статусом `repeat` (дубли) до записи в БД.

Сохраняем в БД только поля: `date`, `status`, `mobile_tel`, `site`, `mobile_operator`.

## 2.6. Логика источников

### 2.6.1. Парсинг имени и оператора

- Провайдер отдаёт тег вида `B111_74951270967_20168`.
- Очистка имени: убрать префикс "ID оператора связи" перед первым `_` и суффикс "ID источника" после последнего `_`, оставить только номер/домен между ними (в примере — `74951270967`).
- Маппинг оператора по префиксу:
  - `B111` → Ростелеком
  - `B222`, `B223` → Билайн
  - `B333` → МТС
  - `B444` → Мегафон

### 2.6.2. Расчётные поля таблицы источников

- Доля нецелевых = `("Лидов" данного источника) / (кол-во строк в разделе "Лиды", где Лиды.site == Источники.name AND статус = "Не целевой") * 100`
- Продаж = `COUNT(строк в Лиды WHERE Лиды.site == Источники.name AND статус = "Купил")`
- Статус = `norm_work == true` → активен, иначе не активен.

### 2.6.3. Кнопка "три точки" (включить/выключить источник)

- Включить → `norm_work=true`, `limit=50`
- Выключить → `norm_work=false`, `limit=0`
- Реализуется через `PATCH /v1/vdl/api/tags/update/{tag_id}`.

### 2.6.4. Автоматизация тегов (ежедневно в 18:00)

1. **Автоматическая чистка** (если включена в настройках проекта): для тегов с `new_answer ≥ "мин. контактов на 1 лид"` (фильтрация за 28 дней) — если `conversion < "Мин. конверсия"`, тег выключается (`norm_work=false`, `limit=0`).
2. **Автоматическое управление** (если включено): для тегов с `conversion ≥ "Мин. конверсия"` — тег включается (`norm_work=true`, `limit=50`).
3. Оба правила выполняются одним пакетным запросом `PATCH /v1/vdl/api/tags/update` (`tag_ids` + общий `update_tag_schema`).

### 2.6.5. Скрытая функция: автообработка источников типа "домен"

Цель: после добавления источника-сайта включить автосбор номеров (заявки роботом), но выключить сам тег сайта, чтобы обычные посетители сайта не считались лидами.

Последовательность (через ~5 минут после добавления источника с `source_type=domain`):

1. `GET /v1/vdl/api/sources/get_by_project/{crm_id}` — отфильтровать источники по `source_type=domain`.
2. `POST /v1/vdl/api/sources/update_settings` — массово выставить этим источникам `parse_phone=false`, `parse_ishod=true`.
3. `GET /v1/vdl/api/tags/get_by_project_and_date/{crm_id}` — получить теги с агрегатами.
4. Отфильтровать теги `filter_by_type=domain`.
5. `PATCH /v1/vdl/api/tags/update` — этим тегам поставить `norm_work=false`, `limit=0`.

## 2.7. Финансовая логика

Никаких API-запросов к провайдеру в этом разделе — вся логика внутренняя.

### 2.7.1. Формирование счёта

1. Данные плательщика подставляются в Google Docs-шаблон: https://docs.google.com/document/d/1u2srF5ifs7oWWqDbQkXCW6mztPRk_Jw1WICNa8Vli5k
2. Итоговая сумма = введённое количество штук × цена (лида/пакета/контакта — берётся из типа проекта, заданного в мастер-кабинете → Проекты).
3. Результат — скачиваемый PDF.
4. Автоматически создаётся запись в мастер-кабинете (раздел Платежи) со статусом "ожидает оплаты" и суммой из шага 2.

### 2.7.2. Закрывающие документы (Акт)

1. Мульти-выбор платежей.
2. Дата начала = дата самого раннего выбранного платежа; дата окончания = текущая дата.
3. Заполнение шаблона: https://docs.google.com/document/d/1ROOb5jLqyqxQ2D2-QQ-xLaLQHta1h5gkxBb39gReVuE
4. Данные плательщика — из раздела "Плательщик".
5. Результат — PDF.

### 2.7.3. Баланс (₽)

- При смене статуса платежа на "оплачено" в мастер-кабинете сумма автоматически зачисляется на баланс кабинета.
- Если баланс ≥ 0 — сумма прибавляется. Если баланс отрицательный (долг) — сумма также прибавляется (то есть сначала гасится долг, остаток идёт в плюс).

### 2.7.4. Баланс (количество штук)

- Тип проекта определяет, что списывается за единицу:
  - `квалы` → списание за каждый лид, добавленный в разделе Лиды.
  - `пакет` → списание за каждый контакт в разделе Контакты.
  - `номера` → списание за каждый контакт в разделе Контакты.
- Количество штук берётся из последнего оплаченного счёта:
  - Если тип проекта **не менялся** с прошлого счёта — новое количество **добавляется** к остатку (пример: было 170/180, докупили 200 → 370/380 либо аналогично по логике "к остатку").
  - Если тип проекта **изменился** — количество **не суммируется**, а полностью заменяется, счётчик использованных обнуляется (пример: было 170/180, оплатили 200 нового типа → становится 0/200).

## 2.8. Логика мастер-кабинета: аналитика

### 2.8.1. Статистика по менеджерам (за выбранный месяц)

1. Список активных проектов менеджера на начало месяца (снапшот на дату ≤ 7-е число включительно).
2. Количество платежей за месяц по проектам этого менеджера.
3. Сумма этих платежей.
4. Retention = `(п.2) / (п.1) * 100`.
5. Бонус менеджера = `(п.3) * 10%`.

### 2.8.2. Статистика по клиентам (за выбранный месяц)

1. Все проекты, по которым были платежи в этом месяце.
2. Ранжирование по совокупной сумме платежей (убывание).

### 2.8.3. Создание проекта из мастер-кабинета

1. Форма → API-запрос `POST /v1/crm/open-api/projects` с типом, названием, регионом, статусом `active`. Итоговое имя проекта формируется по шаблону: `"{Регион}/Peremoney ЛКП {Тип}/{Сфера}/{Название клиента}"` (пример: "Москва/Peremoney ЛКП VDL/Коррекция зрения/Имплантсити").
2. Одновременно создаётся внутренняя запись кабинета (см. 2.1) с автогенерацией логинов/паролей.
3. **Важно**: ручка создания проекта не идемпотентна — повтор запроса после таймаута (504) может создать дубль. Нужна защита от повторной отправки на нашей стороне (debounce / идемпотентный ключ).

### 2.8.4. "Связать с другим" (клонирование кабинета)

- Копия существующего кабинета без вызова API создания проекта у провайдера.
- Разрешено менять: название (обязательно, должно отличаться), тип, цену, менеджера.

# 3. ВНЕШНИЕ API-ПРОВАЙДЕРЫ (Leads Factory OpenAPI)

Базовый URL: `https://openapi.leads-factory.ru/v1/`
Авторизация: Bearer-токен `60286a84-65eb-42ae-b0ee-4b33aecd6c3f` (передаётся в заголовке `Authorization`).
Документация Swagger: https://openapi.leads-factory.ru/v1/docs

## 3.1. CRM API (заявки, проекты, интеграции)

### `GET /v1/crm/open-api/projects/{project_id}/answers`

Список заявок (контактов/лидов) проекта.
Параметры (query): `date_from`, `date_to`, `date_updated_from`, `date_updated_to`, `status` (array, полный список значений см. 2.5 — provider-side справочник шире нашего отображаемого), `mobile_tel`, `order` (`asc`/`desc`, default `desc`), `page` (default 1), `limit` (default 50, max 200).
Ошибки: 401 (невалидный токен), 422 (ошибка валидации), 502 (ошибка CRM), 504 (CRM недоступен).
Использование: раздел Контакты (11:00 и 15:00) и раздел Лиды (фильтр по успешным).

### `GET /v1/crm/open-api/answers/{answer_id}/calls`

Ссылки на записи звонков по заявке. Ответ: `items: [{link, date}]`.
Использование: кнопка "Запись" в разделе Лиды.

### `PATCH /v1/crm/open-api/projects/{project_id}`

Редактирование проекта. Body: `name`, `regions[]`, `client_regions[]`, `sphere`, `status`, `work_client_status`, `timezone`, `call_center_status`, `experiment`, `uniq`, `late_experiment_delta_hours`, `transfer_to_manager`, `transfer_to_manager_phone`, `transfer_to_manager_api_delay`, `additional_columns[]`.
Использование: раздел Настройки (кнопка "СОХРАНИТЬ НАСТРОЙКИ"), расписание работы (20:00), мастер-кабинет → Проекты → кнопка "Управлять" (Отключить/Включить).

### `POST /v1/crm/open-api/projects`

Создание проекта. Body: `name`, `type` (id из `/projects/types`), `regions[]`, `status`. Ответ: `{id}`.
⚠️ Не идемпотентна — повтор после 504 может создать дубль.
Ошибки: 400, 401, 403, 409 (имя занято), 422, 502, 504.
Использование: мастер-кабинет → "Создать проект".

### `GET /v1/crm/open-api/projects/types`

Справочник допустимых типов проектов для создания. Ответ: `items: [{id, name}]`.

### `GET /v1/crm/open-api/projects/{project_id}/script`

Скрипт оператора КЦ (сырой HTML). Ответ: `{project_id, name, script, script_lvl}`.
Использование: раздел Скрипт (обновление в 20:00).

### Интеграции CRM/мессенджеры (единообразный паттерн `GET /v1/crm/open-api/projects/{project_id}/integrations/{name}`)

Список из документа (все — параметр `project_id` в пути):

- `.../integrations/telegram` — Telegram
- `.../integrations/bitrix` — Bitrix24
- `.../integrations/amocrm` — AmoCRM
- `.../integrations/email` — Email

> В ТЗ указано: "Есть все кроме MAX, его тоже нужно". Полный набор интеграций (мессенджеры + CRM) должен быть уточнён у провайдера/в Swagger-документации (`/v1/docs`) — в выгруженном фрагменте явно присутствуют Telegram, Bitrix24, AmoCRM, Email; интеграция MAX отсутствует в провайдерском API и требует отдельного уточнения (возможно, добавляется на нашей стороне как отдельный канал, не через Leads Factory).
> Внешний вид полей форм интеграции — копировать из `lk.leads-factory.ru`.

## 3.2. VDL API (источники / теги)

### `GET /v1/vdl/api/tags/get_by_project_and_date/{crm_id}`

Список тегов проекта с агрегатами за период (аналог `/get_by_project`, но с агрегацией по `start_date..end_date`).
Параметры: `page` (default 1), `limit` (default 20), `start_date`, `end_date`, `tag_search`, `show_locked` (default `false`), `filter_by_norm_work` (bool|null), `filter_by_unsucess_block` (bool|null), `filter_by_label`, `filter_by_type[]`, `filter_by_status[]` (`active`/`inactive`/`wait_on`/`wait_off`), `sort_by` (`limit`/`sebes`/`success`/`new_answer`/`fuck_limit`), `sort_order` (`asc`/`desc`), `sebes_min`.
Использование: раздел Источники (ежедневная выгрузка в 09:00, фильтр по периоду), скрытая функция автообработки доменов (шаг 3).

### `GET /v1/vdl/api/sources/get_by_project/{crm_id}`

Список источников проекта (без агрегатов), для управления парсингом. Параметры: `page`, `limit`, `phone_search`, `phone_type_search`, `will_work` (`In work`/`Not in work`/`Not checked`), `hidden` (`only_visible`/`only_hidden`/`all`, default `only_visible`), `source_type` (`phone`/`domain`), `parse_ishod` (bool), `parse_phone` (bool), `filter_by_label`.
Использование: скрытая функция автообработки доменов (шаг 1).

### `PUT /v1/vdl/api/sources/add_all/{crm_id}`

Пакетное добавление источников. Body: `source[]`, `subsource`, `source_from`, `source_type` (`phone`/`domain`), `active_duplicate_source` (bool), `label`, `label_color`, `geo_ids[]`.
Использование: кнопка "Добавить источник".

### `POST /v1/vdl/api/sources/update_settings`

Массовое обновление настроек парсинга источников. Body: похожая схема + `active_subsource`, флаги `parse_phone`/`parse_ishod`.
Использование: скрытая функция автообработки доменов (шаг 2).

### `PATCH /v1/vdl/api/tags/update/{tag_id}`

Точечное обновление одного тега (частичное, null-поля игнорируются). Body (`UpdateTagSchema`): `norm_work`, `limit`, `sebes_block_days`, `manual_locked`.
Использование: кнопка "три точки" у источника (включить/выключить).

### `PATCH /v1/vdl/api/tags/update`

Массовое обновление тегов. Body: `{update_tag_schema: {...}, tag_ids: [...]}`.
Использование: автоматизация тегов (18:00 ежедневно), финальный шаг скрытой автообработки доменов.

### `GET /v1/vdl/api/tags/available_tags_types` _(упомянут в ТЗ без полной спеки — уточнить схему ответа в Swagger)_

Использование: список типов тегов для формы "Добавить источник".

## 3.3. Общие правила по ошибкам API

Типовые коды ошибок, встречающиеся почти во всех методах — обрабатывать единообразно на нашей стороне:

- `401` — невалидный/просроченный токен → инициировать переавторизацию/алерт.
- `403` — нет доступа к API-методу.
- `404` — сущность не найдена (проект/заявка).
- `409` — конфликт (например, имя проекта уже существует).
- `422` — ошибка валидации (FastAPI/Pydantic формат: `detail: [{loc, msg, type, input, ctx}]`).
- `502` — внутренняя ошибка CRM/обработки.
- `504` — сервис/CRM временно недоступен (для не идемпотентных методов, например создания проекта — требует ретрай-политики с идемпотентным ключом на нашей стороне, не просто повтор запроса).
