### DEF-03 — НЕ закрыт; первопричина установлена точно, блокеров два

**Диагностика стала возможна** после того, как в `TochkaApiException` добавили `providerDetails` — тело ответа банка больше не теряется. Точка называет отклонённое поле прямым текстом:

```
POST /api/cabinets/{id}/finance/invoices  {"quantity":1,"idempotencyKey":"<uuid>"}
→ 502 {"providerStatus":400,"providerDetails":{"Errors":[{"errorCode":"Validation Error",
       "message":"Field Content-Invoice-number : Input should be a valid string; "}]}}
```

Воспроизведено дважды подряд, id ошибок банка `7055ddb5-…` и `bf82e915-…`.

#### Блокер A — дефект кода: `number` должен быть строкой, а не числом

`server/src/tochka/tochka-invoice.ts:34`:

```ts
number: Number(input.invoiceNo),   // отправляет JSON-число; Точка требует string
```

История дефекта показательна. Изначально `invoiceNo` имел вид `1787510529744-8c009864`, `Number(...)` давал `NaN` → в JSON уходил `null` → 400. Правка сделала `invoiceNo` полностью числовым, поэтому теперь уходит валидное число `178751367155805` — и банк **всё равно** отклоняет, потому что ожидает строку. Комментарий в коде «Tochka expects a JSON number» противоречит фактическому контракту API.

**Гипотеза проверена экспериментально.** Поднят изолированный инстанс приложения на порту 4099 с preload-скриптом, который подменяет `Content.Invoice.number` на строку в исходящем запросе (репозиторий при этом не изменялся):

```
[PATCH] number 178754392101513 (number) -> строка
→ ошибка «Field Content-Invoice-number» ИСЧЕЗЛА
```

Валидация тела прошла полностью — запрос дошёл до следующей стадии. Это доказывает, что тип поля и есть причина 400.

**Фикс — одна строка:** `number: input.invoiceNo` (без `Number()`).

**Отдельно: юнит-тест закрепляет неверный контракт.** `src/tochka/tochka-invoice.spec.ts:16` ожидает `number: 42` — число. Тест зелёный и при этом защищает дефект. Его нужно поправить вместе с кодом, иначе правка «сломает» тест и может быть отменена.

#### Блокер B — окружение: у токена Точки нет прав на выставление счетов

После устранения ошибки валидации запрос дошёл до проверки прав и получил:

```
→ 502 {"providerStatus":403,"providerDetails":{"Errors":[{"errorCode":"Something going wrong",
       "message":"Forbidden by consent"}]}}
```

Read-only проверка выданных согласий подтверждает причину:

```
GET https://enter.tochka.com/uapi/v1.0/consents  → 200
    permissions: ['ReadCustomerData']
```

У `TOCHKA_JWT` выдано **только** `ReadCustomerData`. Для создания счетов нужен `ManageInvoiceData`, для вебхуков — `ManageWebhookData`; оба требования зафиксированы в `server/README.md:28`. Это не дефект кода — токен нужно перевыпустить в кабинете Точки с нужными согласиями. Ровно этот пункт числится незакрытым в `WORKLOG.md:37` («live-остаток: заполнить новый `TOCHKA_JWT`…»), то есть боевой путь создания счёта никогда не подтверждался живым вызовом.

Прочая read-only диагностика: `GET /open-banking/v1.0/accounts` → 200 с пустым `Data.Account` (следствие того же отсутствия прав); `GET /invoice/v1.0/bills/{customerCode}` → 501 `HTTPNotImplemented`; payload JWT содержит только `customer_code`, совпадающий с `TOCHKA_CUSTOMER_CODE`.

#### Что нужно для закрытия DEF-03

1. `number: input.invoiceNo` в `tochka-invoice.ts` + поправить ожидание в `tochka-invoice.spec.ts`.
2. Перевыпустить `TOCHKA_JWT` с согласиями `ManageInvoiceData` и `ManageWebhookData`.
3. После этого повторить сквозной прогон `E2E-003`; только тогда станут проверяемы `FIN-007`, `FIN-009` (PDF), `FIN-010`, `FILE-006` и `MPAY-001` в части «юр. лицо».

**Побочный эффект (`FIN-012`) подтверждён:** каждая неудачная попытка оставляет платёж `PENDING` с `invoiceCreationStatus = FAILED`, попадающий в метрику «Ожидается». За время ретеста накопилось 6 таких фантомных записей по 250 ₽; они удалены, метрика «Ожидается» вернулась к 1750 ₽. Само поведение остаётся дефектом: неудачное создание счёта не должно порождать видимый пользователю ожидающий платёж.

**Заблокировано этим дефектом:** `FIN-007`, `FIN-009` (PDF), `FIN-010`, `FILE-006`, `MPAY-001` в части «юр. лицо», сценарий `E2E-003`.

### DEF-07 — закрыт

В `Payment` добавлены поля снимка (`totalUnitsBefore`, `usedUnitsBefore`, `balanceTypeBefore`, миграция №14), которые заполняются при оплате и восстанавливаются при откате.

```
оплата VDL 10 шт            → 2500 ₽, 10 шт, исп. 0, VDL
оплата VDL 4 шт             → 3500 ₽, 14 шт, исп. 0, VDL
имитация расхода 6 из 14    → 3500 ₽, 14 шт, исп. 6, VDL
оплата ПАКЕТ 7 шт           → 5250 ₽,  7 шт, исп. 0, PACKAGE
откат ПАКЕТ  → ожидает      → 3500 ₽, 14 шт, исп. 6, VDL   ✅ лимит и расход восстановлены
откат VDL 4  → ожидает      → 2500 ₽, 10 шт, исп. 0, VDL
откат VDL 10 → ожидает      →    0 ₽,  0 шт, исп. 0, null
```

Отрицательного `totalUnits` больше не возникает. Добавлены два защитных условия, оба проверены:

- откат «через один» — `409 «Сначала отмените более поздний оплаченный платёж»`, состояние не меняется;
- откат платежа без снимка (старые записи) — `409 «Для старого платежа нет snapshot баланса; требуется ручная сверка»`, состояние не меняется.

Второе условие важно: вместо тихой порчи баланса система теперь требует ручного разбора.

### REG-01 · P1 · НОВОЕ — отказ провайдера блокирует сохранение любых настроек

**Требования:** `SET-013`, `SET-001`, `NAV-004`, раздел 16.2.

Исправление DEF-08 качнуло маятник в другую сторону: раньше статус не доходил до провайдера, теперь недоступность провайдера лишает возможности сохранить вообще что-либо в разделе «Настройки» — включая параметры, к провайдеру никакого отношения не имеющие.

```
кабинет QAC-C-numbers (providerProjectId=903, у провайдера отсутствует)
состояние до:  contactsVisible=True  tz=3  crm='bitrix'
PATCH /settings — скрыть «Контакты» для клиента, сменить tz и CRM  → HTTP 404
состояние после: contactsVisible=True  tz=3  crm='bitrix'   ← не сохранено ничего
```

Последствие: при недоступности Leads Factory сотрудник не может ни скрыть раздел от клиента, ни сменить часовой пояс, ни настроить интеграции. Флаги видимости — это механизм разграничения доступа, и он становится заложником внешнего API.

`SET-013` требует, чтобы атомарность локальных и внешних изменений была **определена**. Сейчас выбран самый жёсткий вариант («всё или ничего») без явного решения. Разумный компромисс: сохранять локальные поля всегда, а внешний вызов делать отдельно — с явным индикатором «статус провайдеру не передан» и возможностью повтора.

### Новые находки

**DEF-35 · P3 · `formatPhone()` не имеет отказоустойчивого форматирования для нестандартной длины номера**
`client/src/shared/lib/format.ts:29-35` — регэксп `^7?(\d{3})(\d{3})(\d{2})(\d{2})$` матчит только 10/11 цифр; при несовпадении функция возвращает **сырую строку без изменений**. Живой репро: контакт с `mobileTel="790066611738"` (12 цифр, создан вручную через обратную связь/фидбек, не через провайдера) отображается в «Контакты» и «Лиды» как `790066611738` — без `+7`, пробелов и дефисов, — тогда как соседние строки показывают `+7 495 127-09-68`. Нарушает заявленное в разделе 16.4 «единообразное форматирование»; не влияет на данные, только на отображение.

**Наблюдение (не дефект) · Лиды/Контакты не используют серверный поиск/фильтр по датам — `DEF-05` не достижим из UI**
`client/src/entities/leads/api/leads-api.ts:28` и `entities/contacts/api/contacts-api.ts:11` — `fetchLeads`/`fetchContacts` не принимают `search`/`dateFrom`/`dateTo`; клиент загружает **весь** список кабинета один раз и фильтрует/ищет в браузере. Проверено сетевым логом: поиск по телефону, смена статуса-фильтра и инверсия диапазона дат (`dateFrom > dateTo`) на странице «Лиды»/«Контакты» не порождают ни одного нового запроса к `4010`. Практическое следствие: ранее задокументированный **DEF-05** (`GET /leads?search=...` → 500) реален на уровне API, но **недостижим через реальный UI** — эндпоинт, на котором он воспроизводится, клиент не вызывает. Это не отменяет дефект (прямой вызов API остаётся уязвимым, а сам подход «тянуть весь список в браузер» не масштабируется на кабинеты с тысячами лидов), но меняет его практический риск с «ломает поиск в интерфейсе» на «мёртвый код на сервере плюс архитектурный потолок производительности» — стоит учесть при приоритизации.

**DEF-36 · P2 · Сессия в общем `localStorage` — вход в одной вкладке молча подменяет личность во всех остальных**
Подтверждено двумя независимыми репро в двух вкладках одного окна Chrome:
1. Вкладка 1 вошла как `qac_a_full` (FULL). Вкладка 2 открывает `/login` — вместо формы входа происходит мгновенный редирект на `/dashboard` **с личностью вкладки 1** (ключ `peremoney.session` в `localStorage` общий на origin, проверено через `localStorage.getItem`). Логин-форма для второго пользователя недостижима, пока не разлогиниться.
2. После явного логаута и входа как `qac_a_ltd` (LIMITED) во вкладке 2, вкладка 1 (всё ещё открытая на `/leads` с данными FULL) при следующей навигации **без перезагрузки и без предупреждения** отрисовалась как кабинет LIMITED (3 пункта меню, бейдж «Ограниченный доступ») — сотрудник, работавший в вкладке 1, увидел бы чужие данные под видом продолжения своей сессии.

### DEF-01 · P0 · Двойное зачисление платежа при конкурентном изменении статуса

**Требования:** `MPAY-010`, `MPAY-004`, `BAL-010`, раздел 16.2 «финансовые операции атомарны», раздел 20.
**Где:** `server/src/finance/finance.service.ts:118` — `setPaymentStatus`.

`findUnique` внутри транзакции не берёт блокировку строки. При READ COMMITTED две транзакции одновременно видят `status = PENDING`, обе проходят проверку `if (payment.status === status) return payment` и обе применяют `increment`. `externalKey` записи баланса содержит `Date.now()`, поэтому уникальный индекс дубль тоже не ловит.

**Воспроизведение** (платёж 2500 ₽ / 10 единиц, 10 параллельных запросов, 3 прогона подряд):

```
прогон 1: moneyBalance=22500  totalUnits=90   (верно: 2500 / 10)
прогон 2: moneyBalance=15000  totalUnits=60
прогон 3: moneyBalance=12500  totalUnits=50
```

Реестр платежей и баланс разошлись в 4 раза, и **ни одна проверка в системе этого не замечает**. В UI «Финансы» показывается только количественный баланс, поэтому расхождение денег пользователю не видно вообще.

**Ориентир для исправления:** рабочий образец блокировки уже есть в этом же репозитории — `scheduler.service.ts:96` и `domain-source-jobs.service.ts` используют `SELECT … FOR UPDATE SKIP LOCKED`. Второй вариант — детерминированный `externalKey` (`PAYMENT:{id}` без `Date.now()`), тогда уникальный индекс сам отсечёт дубль.

### DEF-02 · P0 · Конкурентная доставка fan-out создаёт дубли лидов и списаний

**Требования:** `FAN-007`, `BAL-003`, `BAL-009`, `FAN-013`, `E2E-005`.

### DEF-04 · P1 · Конец периода не включает последний день — дашборд расходится со списками

**Требования:** `DASH-003`, `MDASH-001`, `CRON-012`, `E2E-010`.
**Где:** `server/src/finance/finance.service.ts:232` — `range()`.

`lte = new Date(query.dateTo)` для `"2026-08-23"` даёт `2026-08-23T00:00:00Z`, то есть весь последний день периода отбрасывается. Клиент присылает именно календарные даты, и `client/src/shared/lib/date.ts:11` прямо документирует их как включительные: «Диапазон в N дней, заканчивающийся сегодня (включительно)».

**Ключевая улика — расхождение внутри одной системы.** `crm.service.ts:69` тот же случай обрабатывает правильно (`${to}T23:59:59.999Z`). Один и тот же период даёт разные ответы:

```
данные: 4 контакта 10.08, 3 контакта 11.08, 3 контакта 12.08 (все в 10:00Z)

GET /contacts?dateFrom=2026-08-10&dateTo=2026-08-12   → 10 контактов ✅
GET /dashboard?dateFrom=2026-08-10&dateTo=2026-08-12  →  7 контактов ❌
GET /dashboard?dateFrom=2026-08-10&dateTo=2026-08-10  →  0 контактов ❌ (за целый день данных)
```

**Второе проявление, `MDASH-001`.** Кнопка «Весь год» строит `to = сегодня` и показывает **ноль платежей**, хотя платёж на 2500 ₽ создан сегодня и в срезе «Август 2026» (`to = 2026-08-31`) отображается. Скриншот мастер-дашборда: «Платежей за период нет».

**Влияние:** данные текущего дня отсутствуют на дашборде всегда; выбор одного дня даёт пустой результат; выручка, CPL, CR и бонусы менеджеров занижены на последний день любого периода.

### DEF-05 · P1 · Поиск лида по номеру телефона возвращает HTTP 500

**Требования:** `LEAD-013`, `LEAD-014`, раздел 22 (входит в regression gate).
**Где:** `server/src/crm/crm.service.ts:27`.

### DEF-10 · P1 · Мастер-аналитика: снапшот на 7-е число не реализован, правильная реализация лежит мёртвым кодом

**Требования:** `MDASH-002`, `MDASH-003`, `MDASH-005`, `Q-010`.

Сервер (`finance.service.ts:207`) считает активные проекты как `p.isActive && p.createdAt <= range.gte` — по **текущему** флагу активности и по началу периода, без какого-либо снапшота.

**Отдельная проблема качества:** правильная реализация правила существует в `client/src/entities/master-payments/lib/managerStats.ts` — с корректным `getSnapshotDate` (7-е число) и учётом платежей по `createdAt`. Зелёные тесты создают ложную уверенность, что `MDASH-002` реализован.

Прочее по мастер-аналитике: `MDASH-006` бонус = 10 % от суммы — верно (2500 ₽ → 250 ₽). `MDASH-007` рейтинг клиентов по убыванию суммы — верно. `MDASH-008` вторичный ключ сортировки при равных суммах отсутствует. `MDASH-004` платежи привязаны к менеджеру и периоду по `paidAt`, что фиксирует ответ на `Q-009` в пользу даты оплаты (клиентская реализация использует `createdAt` — ещё одно расхождение двух реализаций).

## 8. Как воспроизвести

# двойное зачисление (DEF-01) — 10 параллельных запросов
for i in $(seq 1 10); do
