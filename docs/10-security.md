# Безопасность

## Реализованные меры

- Bearer JWT подписывается серверным секретом; пользователь повторно читается из БД на каждый запрос.
- Logout и деактивация сессии используют `sessionVersion`.
- Пароли кабинетов хранятся как bcrypt hashes; сгенерированные credentials возвращаются при создании, а не читаются из БД.
- Guards проверяют роль, принадлежность кабинету и видимость раздела на backend.
- `ValidationPipe` удаляет неизвестные поля и преобразует DTO.
- Helmet включает базовые защитные HTTP headers.
- Login и публичный fanout имеют IP rate limit.
- Webhook Точки проверяет RS256-подпись и идемпотентность события.
- Ошибки провайдера очищаются от потенциально чувствительного `input`.
- CSV-экспорт нейтрализует formula injection.
- Счета и создание проектов защищены idempotency state machine.

## Правила эксплуатации

- Секреты задаются только окружением/secret manager; не хранить их в Markdown, git, frontend или screenshots.
- Использовать отдельные БД и provider projects для dev/QA/prod.
- Ограничить CORS production origin: текущая конфигурация `origin: true` подходит локальному стенду, но слишком широка для публичной среды.
- Размещать API за TLS reverse proxy, включить централизованные логи и алерты readiness/scheduler.
- Регулярно выполнять `npm audit`, обновлять зависимости и проверять lockfiles.
- Ротировать JWT/provider/bank/Telegram secrets после утечки.
- Не логировать Authorization, банковский JWT, телефоны целиком и реквизиты плательщика.

## Остаточные риски

- In-memory rate limiter не координируется между несколькими instance и сбрасывается при рестарте; для scale-out нужен Redis/gateway.
- CORS разрешает отражённый origin с credentials и требует production allowlist.
- Положительный end-to-end тест Точки зависит от реального контролируемого плательщика, PDF и webhook.
- `UNCERTAIN` внешние операции требуют отдельного reconciliation runbook, чтобы не создать дубликат.
- Retention и маскирование персональных данных должны быть утверждены организационной политикой.
